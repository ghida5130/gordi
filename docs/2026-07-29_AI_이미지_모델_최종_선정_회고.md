### 3.1 1차: 7개 후보를 같은 화면에서 비교했다

평가 부담을 줄였다.

### 3.3 1차에서 발견한 문제를 2차 조건에 반영했다

1차 결과만으로 최종 모델을 정하지 않은 가장 큰 이유는 테스트 입력이 실제
서비스 조건을 충분히 반영하지 못했기 때문이다.

#### 고정 핏 태그의 한계

같은 옷도 사용자가 선택한 사이즈와 아바타 체형에 따라 핏이 달라지는데, 1차에는
의상마다 `슬림핏`, `오버핏` 같은 태그가 고정돼 있었다.

#### 착용컷 인물 오염

의상 레퍼런스에 모델이 포함되면 선택한 마네킹 대신 레퍼런스 속 인물의 얼굴이나
체형을 결과에 사용하는 문제가 있었다.

#### 서비스 입력과 테스트 입력의 차이

초기 테스트는 상세 신체 치수를 직접 입력받았지만 실제 MVP 사용자는 성별, 키,
몸무게와 사전제작 아바타만 선택한다.

#### 단일 의상 중심의 케이스

단일 의상은 프롬프트 준수율을 분석하기 좋지만 실제 사용에서는 상의와 하의를
함께 입히는 경우가 더 많다.

### 3.4 2차: 실제 서비스와 가까운 평가로 바꿨다

2차는 상위 4개 모델만 남겨 Run당 비교 수를 21개에서 6개로 줄이고, 줄어든 평가
부담을 입력 품질과 케이스 다양성 개선에 사용했다.

#### MVP 입력으로 단순화

- 성별
- 키
- 몸무게
- 사전제작 아바타

상세 신체 기준은 서버가 아바타 프리셋과 키·몸무게를 이용해 계산했다.

#### 선택 사이즈 기반 동적 핏

`relative-fit-v1` 규칙으로 판매 페이지의 선택 사이즈 실측과 아바타 기준 치수를
비교했다.

- 상의: 가슴 여유량, 어깨 차이, 소매 차이, 총장 비율
- 하의: 허리·힙 여유량, 밑위, 허벅지와 밑단 비율, 총장
- 결과: `TIGHT`, `REGULAR`, `RELAXED`, `DROPPED`, `WIDE`,
  `HIGH_RISE` 등의 아바타 상대 핏

프론트 태그는 입력 확인용으로만 사용하고, 서버가 원시 치수로 최종 태그와
프롬프트를 다시 생성했다.

#### 이미지 역할 분리

`canonical-v2-fit-aware` 프롬프트는 레퍼런스 권한을 다음과 같이 분리했다.

- `PERSON BASE`: 얼굴, 신체, 체형, 비율, 포즈와 카메라의 유일한 기준
- `GARMENT ONLY`: 의류의 색상, 로고, 패턴, 재질과 구조만 참고

착용컷 속 인물과 함께 보이는 다른 의상은 무시하고, 입력이 충돌하면 항상
`PERSON BASE`를 우선하도록 했다.

#### 데이터셋 확장

무신사 상품을 기반으로 기존 단일 의상 6개와 상·하의 조합 6개를 준비했다.
여성 하의가 없던 문제를 보완해 부츠컷, 파라슈트와 와이드 슬랙스를 추가했다.

각 의상에는 선택 사이즈 실측, 착용컷 여부, 출처와 이미지 해시를 기록했다.

## 4. 최종 선택 근거

### 4.1 1차 세부 신호가 2차에서 확대됐다

1차에서는 종합 3위였지만 상위 3개의 점수 차이가 0.8점 이내였고, 체형 보존
1위와 최다 승리라는 강한 세부 지표가 있었다. 더 실제적인 조건으로 바꾼
2차에서는 이 잠재력이 종합 1위로 분명하게 나타났다.

2026-08-05 재검증에서는 1차의 정확한 순위가 평가자·시나리오 가중 방식에 따라
달라지는 것도 확인했다. 따라서 “1차부터 같은 모델이 일관된 1위였다”는 뜻이
아니다. 1차의 근거는 상위권 후보를 넓게 남길 만한 신호였고, 최종 선택의 핵심
근거는 더 실제적인 조건에서 순위가 안정된 2차 결과다.

### 4.2 가상 피팅의 핵심 품질을 모두 만족했다

가상 피팅은 보기 좋은 이미지만 만드는 문제가 아니다. 선택한 옷과 아바타가
동시에 유지돼야 한다.

`Nano Banana 2`는 다음 항목을 한쪽에 치우치지 않고 모두 충족했다.

- 의류의 로고·그래픽·색상과 실루엣 보존
- 선택한 아바타의 체형과 비율 유지
- 상의와 하의를 동시에 적용할 때의 자연스러운 착용감
- 손, 소매, 허리선과 다리 주변의 생성 결함 억제

### 4.3 품질 대비 속도와 비용이 가장 합리적이었다

FLUX.2 Max는 두 배 이상 느리면서 품질도 낮았다. 최종 선택에서 `Nano Banana 2`
정도의 추가 대기시간은 품질 향상을 위해 감수할 가치가 있다고 판단했다.

종합점수에서 22.1점 앞서므로, 현재 평가 규모에서는 추가 비용보다 품질 향상의

### 4.4 2차 호출 안정성도 확인했다

2차의 32회 실제 호출은 모두 성공했다. 네 모델 모두 후보를 빠짐없이 생성한
동일 조건에서 평가됐기 때문에 1차처럼 모델별 표본 수가 달라지는 문제가 없었다.

## 5. 다른 모델을 최종 선택하지 않은 이유

### GPT Image 2

- 1차 종합 1위였고 자연스러움과 결함 억제가 강했다.
- 2차에서는 의류 보존 3.75에 비해 체형 보존이 3.08로 낮았다.
- 평균 응답시간이 51.0초로 Nano Banana 2보다 두 배 이상 길었다.
- 실제 서비스 조건에서 Nano Banana 2와의 종합점수 차이가 20.2점 발생했다.
- BYOK 직접 청구액은 $1.34로 Nano Banana 2보다 $0.04만 낮았다.

### Nano Banana 2 Lite

- 가장 빠르고 1차에서 균형 잡힌 2위를 기록했다.
- 2차 품질 평균 3.53으로 GPT Image 2보다 높았지만 선호도가 37.4%에 그쳤다.
- 속도 장점만으로 Nano Banana 2와의 22.1점 품질·선호 격차를 상쇄하지 못했다.
- BYOK 직접 청구액은 $0.71로 가장 저렴했지만 최종 품질 격차가 컸다.

### FLUX.2 Max

- 호출 성공률과 결함 억제는 안정적이었다.
- 2차 종합 4위이며 평균 응답시간이 50.2초로 길었다.
- OpenRouter 관리 키로 호출돼 Run 데이터에 비용이 직접 기록됐다.
- 품질, 속도와 비용을 함께 보면 주 모델로 선택할 근거가 가장 약했다.

## 6. 잘된 점

### 6.1 한 번의 순위로 결정하지 않았다

1차 1위 모델을 즉시 선택하지 않고, 1차에서 발견한 입력 문제를 수정한 뒤 상위
4개를 다시 비교했다. 덕분에 “기본 프롬프트에서 잘하는 모델”과 “우리 서비스
조건에서 잘하는 모델”을 구분할 수 있었다.

### 6.2 브랜드를 숨긴 채 933개의 pairwise 투표 기록을 모았다

평가자가 공급자 이름과 사전 기대에 영향을 받지 않고 이미지 자체만 비교했다.
선호 선택과 품질 항목별 점수를 함께 수집해 최종 결정의 이유를 수치로 설명할 수
있게 됐다.

단, 933은 서로 독립적인 이미지 판단 933개를 뜻하지 않는다. 같은 평가자가 같은
Run 안에서 여러 모델 쌍을 연속 평가했으므로 통계적 추론에서는
`평가자 × Run`을 군집 단위로 취급해야 한다.

### 6.3 제품 문제를 평가 설계에 반영했다

고정 핏 태그, 착용컷 인물 오염, 과도한 사용자 입력과 단일 의상 중심 데이터라는
문제를 프롬프트만 수정하는 데 그치지 않고 입력 구조·서버 계산·데이터셋까지
함께 바꿨다.

### 6.4 품질과 운영 지표를 함께 봤다

종합점수뿐 아니라 호출 성공률, 평균 지연시간, OpenRouter 기록 비용과 BYOK
공급자 직접 청구액을 함께 비교했다.
`Nano Banana 2`는 가장 빠른 모델은 아니지만, 선택 가능한 품질을 유지하면서
지연시간이 과도하지 않은 모델이었다.

## 7. 한계와 주의할 점

### 7.1 2차 케이스 분포가 완전히 균형적이지 않다

2차 실제 Run에는 D2와 E3가 각각 두 번 포함됐고, 준비한 E2 조합의 실제 Run은
없다. 대신 단일 의상 A1 케이스가 포함됐다. 최종 순위의 격차가 충분히 크고
1차 세부 지표와 방향이 일치해 모델 선정은 진행하지만, 결과를 모든 의류 유형에
대한 절대적 우위로 해석해서는 안 된다.

### 7.2 평가자별 참여량이 다르다

2차 평가자별 저장 표는 18표에서 42표까지 차이가 있다. 모든 평가자가 모든 Run을
평가한 구조는 아니므로 개인 취향과 케이스 효과가 일부 섞일 수 있다.

### 7.3 동적 핏 규칙은 계속 검증해야 한다

`relative-fit-v1`은 재현 가능한 첫 규칙이다. 허리·힙 여유량과 기장 비율의
임계값이 실제 사용자 체감과 맞는지는 서비스 데이터로 보정해야 한다.

### 7.4 비용 원장이 두 곳으로 분리된다

Google과 OpenAI 모델은 OpenRouter BYOK를 사용하므로 OpenRouter Run의 비용은
0이고 실제 청구는 각 공급자 계정에 남는다. 반면 FLUX.2 Max 등은 OpenRouter가
과금을 처리해 Run에 비용이 기록된다. 전체 비용을 정확히 추적하려면
OpenRouter 사용량과 Google·OpenAI 결제 내역을 함께 수집해야 한다.

현재 총 청구액은 확인했지만 요청별 공급자 직접 비용과 라운드별 비용은 연결되지
않았다. 프로덕션 전에는 요청 단위 비용, 재시도 비용과 월간 예상 사용량을
확정해야 한다.

### 7.5 모델 성능은 고정되지 않는다

공급자 모델 버전이나 OpenRouter 라우팅이 변경되면 같은 모델명에서도 품질과
지연시간이 달라질 수 있다. 최종 선택은 영구 고정이 아니라 현재 버전에 대한
의사결정으로 관리해야 한다.

### 7.6 2026-08-05 재집계 감사: 1차 선별과 2차 선정의 증거 강도가 달랐다

최종 선정 문서와 버전 관리된 933표 스냅샷을 다시 집계하고, 원 집계 외에 동일
평가자 가중, 동일 시나리오 가중, 한 평가자 제외와 한 Run 제외 민감도 분석을
수행했다.

| 검증 관점 | 1차 | 2차 | 해석 |
| --- | --- | --- | --- |
| 원 집계 | GPT Image 2 68.4, Lite 67.7, Nano Banana 2 67.6 | Nano Banana 2 72.7, 2위 52.5 | 1차 상위 3개는 0.8점 이내, 2차는 20.2점 차이 |
| 평가자 동일 가중 | FLUX.2 Max 66.4가 1위로 변경 | Nano Banana 2 72.7, 2위 50.6 | 1차 순서는 참여량 영향에 민감, 2차 1위 유지 |
| 시나리오 동일 가중 | GPT Image 2 68.4, Lite 64.2 | Nano Banana 2 70.4, 2위 53.1 | 2차 중복 케이스 영향을 줄여도 17.4점 차이 |
| 평가자 1명씩 제외 | GPT·Nano Banana 2·Lite 사이에서 1위 변경 | 모든 경우 Nano Banana 2, 차이 17.8~22.1 | 2차 결과가 특정 평가자 한 명에 의존하지 않음 |
| Run 1개씩 제외 | GPT·Nano Banana 2·Lite 사이에서 1위 변경 | 모든 경우 Nano Banana 2, 차이 13.3~25.1 | 2차 결과가 특정 Run 하나에 의존하지 않음 |

1차의 시나리오 동일 가중 결과는 GPT Image 2가 생성 실패 때문에 고유 시나리오
4개 중 2개에서만 관측됐다는 제약이 있어 완전한 공통 케이스 비교는 아니다. 이
불균형 자체가 1차 순위를 최종 champion 근거로 쓰지 말아야 하는 이유다.

이 분석은 1차를 실패한 평가로 만들지 않는다. 오히려 단계별 목적을 더 정확히
설명한다. 1차의 정확한 1~3위 순서는 불안정했지만 어떤 가중에서도 최종 4개
후보군은 상위권을 유지했다. 따라서 1차는 하위 후보를 제거하는 screening으로
적절했고, champion을 정한 근거는 2차의 큰 격차와 민감도 안정성이다.

2차의 Run별 1위만 세면 Nano Banana 2는 8개 중 4개에서 1위였다. 나머지는
FLUX.2 Max 2개, GPT Image 2와 Lite가 각 1개였다. 그럼에도 전체 집계에서
Nano Banana 2가 앞선 이유는 특정 케이스를 독점해서가 아니라 여러 케이스와
평가자에서 상대적으로 높은 선호와 품질을 꾸준히 얻었기 때문이다.

### 7.7 표의 개수와 독립 표본의 개수를 구분해야 한다

버전 관리된 최종 스냅샷의 평가 단위를 다시 세면 다음과 같다.

| 항목 | 1차 | 2차 |
| --- | ---: | ---: |
| pairwise 투표 기록 | 735 | 198 |
| `평가자 × Run` 세션 | 39 | 33 |
| 완주 세션 | 38 | 33 |
| 미완주 세션 | 1개, 3/21표 저장 | 없음 |
| 한 모델의 세션 내 품질 반복 노출 | 최대 6회 | 3회 |
| 모델당 2차 품질 점수 기록 | - | 99개 |
| 모델당 2차 독립 군집 단위 | - | 33개 |

2차는 모든 세션이 완주돼 반복 점수의 단순 평균과 세션별 평균의 중심값이 같다.
하지만 반복 노출 99개를 독립 표본으로 간주하면 신뢰구간이 실제보다 좁아진다.
향후 유의성 검정과 부트스트랩은 반드시 `평가자 × Run` 군집 단위로 수행해야
한다.

1차 최종 스냅샷에는 한 평가자의 3/21표 미완주 세션이 원 집계에 포함됐다.
미완주 세션을 제외하면 GPT Image 2 68.6, Nano Banana 2 67.7, Lite 67.7로
상위권 해석은 같지만 Lite와 Nano Banana 2의 순서가 바뀐다. 이 차이는 1차의
정확한 순위를 과도하게 해석하면 안 된다는 점을 다시 보여준다.

### 7.8 평가 원본은 결정 시점에 불변 스냅샷으로 잠가야 한다

2026-08-05 재검증 당시 데모가 계속 쓰기 가능한 상태여서 1차 Run
`d0eaa713...`에 같은 미완주 평가자의 새 투표 4개가 추가됐고, 작업 트리의 1차
투표 수는 735개에서 739개로 늘었다. 최종 회고의 수치는 버전 관리된 933표
스냅샷을 기준으로 하므로 선정 결론은 바뀌지 않지만, 라이브 저장소를 직접
근거로 삼으면 나중에 같은 문서를 재현할 수 없게 된다.

다음 평가부터는 마감 시점에 원본 JSON을 읽기 전용 스냅샷으로 복사하고 manifest
해시, 프로토콜 버전, 집계 코드 버전과 cutoff 시각을 함께 저장해야 한다. 마감 후
들어온 투표는 다음 평가 배치로 분리한다.

### 7.9 자유 서술 메모만으로 실패 원인을 집계하기 어렵다

2차 198표 중 자유 서술 메모가 있는 표는 7개뿐이었고, 내용도 두 시나리오와 두
평가자에 집중됐다. 메모에서는 레퍼런스 인물 복제, 임의 신발 생성, 의류 색상
변경, 넣어 입기와 소매 길이 불일치가 확인됐다. 이는 중요한 실패 유형이지만
현재 구조로는 모델별 발생률을 계산할 수 없다.

다음 버전에서는 `SOURCE_PERSON_LEAK`, `EXTRA_ITEM`, `COLOR_DRIFT`,
`FIT_MISMATCH`, `BODY_DRIFT`, `ARTIFACT` 같은 다중 선택 실패 태그를 필수 또는
권장 입력으로 두고 자유 메모는 보조 설명으로 사용한다.

## 8. 최종 결정

GORDI 이미지 가상 피팅의 주 이미지 생성 모델은 `Nano Banana 2`
(`google/gemini-3.1-flash-image`)로 한다.

결정 이유는 다음 네 가지다.

1. 1차에서 체형 보존 1위와 전체 최다 승리를 기록했다.
2. 2차 198표 집계에서 종합 1위이며 2위와 20.2점 차이가 났다.
3. 2차 품질 네 항목이 모두 4점 이상으로 유일하게 균형을 충족했다.
4. 100% 호출 성공률과 평균 22.5초로 품질 대비 운영 효율이 가장 좋았다.

평가용 다중 모델 호출은 종료하고, 제품 구현은 Nano Banana 2 단일 모델을
기본 경로로 단순화한다. 다만 장애 대응용 폴백 모델 선정은 이번 품질 평가와
분리해 비용·장애 유형·공급자 독립성을 기준으로 별도 결정한다.

## 10. 최종 회고

이번 평가의 가장 중요한 성과는 7개 모델의 순위를 만든 것이 아니라, 우리
서비스에 필요한 이미지 품질을 구체적으로 정의하고 그 기준으로 하나의 모델을
선택한 것이다.

1차에서는 후보를 넓게 탐색해 가능성이 낮은 모델을 제거했다. 동시에
`Nano Banana 2`가 체형 보존과 승리 횟수에서 강한 신호를 보인다는 사실을
확인했다.

2차에서는 사용자 입력, 동적 핏, 레퍼런스 권한과 상·하의 조합을 실제 서비스와
가깝게 바꿨다. 그 조건에서 `Nano Banana 2`는 품질 네 항목과 종합점수 모두
1위를 기록했고, 속도와 안정성까지 제품에 적용할 수 있는 수준이었다.

사후 민감도 분석을 통해 단계별 역할도 더 분명해졌다. 1차는 순위 변동을 감수한
폭넓은 screening이었고, 2차는 평가자·시나리오 가중과 leave-one-out에도 1위가
바뀌지 않는 최종 검증이었다. 앞으로는 이 분석을 사후 설명이 아니라 평가 시작
전에 정한 종료 조건으로 운영해야 한다.

최종 결론은 다음과 같다.

> 1차는 7개 모델 중 검증할 가치가 있는 4개를 찾는 과정이었고, 2차는 실제
> GORDI 입력 조건에서 가장 적합한 하나를 정하는 과정이었다. 총 933표의 결과를
> 근거로 Nano Banana 2를 주 모델로 사용한다.
