# 발표자료용 정리 — AI 기능 구축 여정

> 발표자료 제작을 위한 핸드오프 문서입니다. (최신화: 2026-08-06)
> 스토리 라인은 크게 5개: **① 착장 이미지 모델 A/B 테스트 → ② 추천 파이프라인 구축 →
> ③ 카탈로그 15k 확장과 TPO 평가 → ④ 트러블슈팅 → ⑤ 지연(latency) 개선**.
> 각 섹션 끝의 "슬라이드 포인트"만 뽑아도 슬라이드 한 장씩 나오도록 구성했습니다.

---

## ① 착장(가상 피팅) 이미지 생성 모델 선정 — 팀 내 블라인드 A/B 테스트

### 스토리: "감으로 고르지 않고, 평가 시스템을 먼저 만들었다"

이미지 생성 모델은 스펙시트만으로 비교할 수 없어서, **모델명을 숨긴 블라인드
A/B 평가 도구를 직접 구축**하고 팀원이 직접 투표하는 방식으로 선정했습니다.

- 평가 도구: 자체 제작 웹 데모 (`ai/image_demo` — FastAPI 백엔드 + React 프론트)
  - 같은 인물/의상 입력으로 여러 모델이 동시에 생성 → 모델명 가린 채 1:1 전수 비교 투표
  - 품질 4개 항목 별도 채점: **의류 보존 / 체형 보존 / 자연스러움 / 결함 억제**
  - 결과 대시보드: 종합 순위, Run별 투표 현황, API 성공률·응답시간·비용까지 자동 집계
- 점수 산식 (선호도 60% + 품질 40%):
  ```
  선호도 = (승 + 0.5×무) ÷ 전체 비교 수 × 100
  품질 환산 = 품질 평균 ÷ 5 × 100
  종합점수 = 선호도 × 0.6 + 품질 환산 × 0.4
  ```

### 1차 평가 (7개 모델) → 2차 평가 (상위 4개)

| 구분 | 1차 | 2차 |
|---|---|---|
| 후보 모델 | 7개 | 상위 4개 (GPT Image 2, Nano Banana 2, Nano Banana 2 Lite, FLUX.2 Max) |
| Run당 비교 쌍 | 최대 21쌍 | 6쌍 (전수 비교 유지, 평가 부담 ↓) |
| 데이터셋 | 프리셋 의상 | 무신사 실제 상품 + 선택 사이즈 **실측치** |
| 핏 처리 | 고정 태그(슬림핏 등) | **동적 핏 계산** (실측 vs 아바타 치수 → TIGHT/REGULAR/RELAXED…) |

2차에서 개선한 핵심 3가지:

1. **레퍼런스 인물 오염을 프롬프트 구조로 해결** — 착용컷 레퍼런스의 인물이 결과에
   섞이는 문제를, "따라 하지 마라" 문구가 아니라 입력 이미지의 **역할 분리**로 해결:
   `PERSON BASE`(인물·체형·포즈의 유일한 기준) vs `GARMENT ONLY`(의상 정보만 참조).
2. **사용자 입력을 MVP로 축소** — 성별·키·몸무게·아바타 선택만 받고, 상세 치수는
   서버가 아바타 프리셋 + 실측으로 계산 (사용자가 어깨너비를 알 필요 없음).
3. **목적별 테스트 케이스 설계** — 사이즈 민감도 4건, 레퍼런스 오염 2건,
   상·하의 조합 6건(남녀 3건씩)으로 검증 목적을 분리.

### 결과: Nano Banana 2 채택

팀원 5명, 누적 84표, 실제 API 호출 24회 전부 성공 기준 중간 집계:

| 순위 | 모델 | 종합점수 | 선호도 | 품질 평균 | 평균 응답 |
|---:|---|---:|---:|---:|---:|
| **1** | **Nano Banana 2** | **79.6** | **77.4%** | **4.15/5** | **22.5초** |
| 2 | GPT Image 2 | 56.3 | 46.4% | 3.56 | 54.3초 |
| 3 | Nano Banana 2 Lite | 40.1 | 25.0% | 3.14 | 15.2초 |
| 4 | FLUX.2 Max | 37.6 | 20.2% | 3.18 | 53.2초 |

- 1위와 2위의 격차 **23.3점** — 품질 4개 항목(의류 보존·체형 보존·자연스러움·결함 억제) **전부 1위**
- 품질 1위이면서 응답시간도 경쟁 모델(GPT Image 2, FLUX.2 Max)의 **절반 이하**
- 이 결과로 실서비스 try-on API(FastAPI)에 Nano Banana 2(gemini-3-pro-image)를 탑재,
  A/B 테스트에서 검증한 PERSON BASE/GARMENT ONLY 프롬프트 구조를 그대로 이식

**슬라이드 포인트**
- "모델 선정을 위해 블라인드 평가 시스템부터 만들었다" (평가 도구 스크린샷 추천)
- 1차 7개 → 2차 4개 깔때기 다이어그램
- 종합점수 막대그래프: 79.6 vs 56.3 (23.3점 차)
- 문제 해결 사례: 착용컷 인물 오염 → 프롬프트 역할 분리 (before/after 이미지 있으면 최적)

## ② AI 추천 파이프라인 구축

### 스토리: "평가 먼저, 튜닝 나중"

추천 품질을 바꾸기 전에 **측정 체계부터 고정**했습니다. 개선이 진짜 개선인지
숫자로 확인할 수 없으면 튜닝하지 않는다는 원칙.

1. 평가 하네스 구축: recall@K, nDCG@K, pairwise 정확도, 다양성, latency 자동 측정
2. 규칙 기반 baseline 고정: **nDCG@10 0.622 / recall@10 0.377** — 이후 모든 변경은 이 기준과 비교
3. 파이프라인 변경 전 오프라인 평가로 회귀 여부 확인이 필수 절차

### 파이프라인 구조 (다이어그램 소스)

```
사용자 무드/조건 (MoodCode, 성별, 카테고리, 예산)
        │
        ▼
① 한국어 질의(TPO 자유 텍스트 포함) → 임베딩 (Gemini Embedding 2, 텍스트+이미지 결합 768차원)
        │
        ▼
② 벡터 인덱스 검색 (상품 15,192건, cosine 유사도 — numpy 행렬 내적)
   ├─ 사전 필터: 성별·카테고리·가격
   └─ 후보 50건 추출
        │
        ▼
③ 규칙 기반 재정렬 (색상·계절·스타일·TPO 태그 + 코디 궁합 점수)
        │
        ▼
④ (opt-in) VLM pairwise 리랭크 — 상위 20건을 비전 모델이 궁합 재판정
        │
        ▼
⑤ 상위 10건 + 근거 기반 추천 이유 반환
   ※ 어느 단계든 실패 시 규칙 기반으로 자동 강등 (추천이 죽지 않음)
```

설계 원칙 3가지:

- **VLM 기능은 전부 opt-in + graceful degradation** — 이미지 속성 추출, 리랭크,
  LLM 추천 이유 모두 플래그로 켜고, 실패하면 규칙 기반으로 조용히 강등
- **VLM 출력은 신뢰하지 않는다** — 속성 추출은 closed vocabulary 밖 값 폐기,
  추천 이유는 fact sheet에 없는 라벨이 나오면 환각으로 간주하고 폐기
- **클라이언트는 OpenAI 호환 1개로 통일** — OpenRouter 상용 모델 ↔ 로컬 Ollama/vLLM을
  endpoint 교체만으로 전환 가능

### 데이터 구축 (파이프라인의 재료)

- 1차(MVP): 무신사 상품 **2,943건** 수집 (수집 정책 v1.1 — 상품 간 3초 간격 등 명문화)
  → **VLM 자동 검수** 파이프라인으로 1,812건 READY 승격 → 최종 **1,991건** 서비스 투입
- 2차(TPO 확장): 4일간 수집으로 정규화 **17,604건**, 서비스 투입 **15,192건**으로 확장
  — 상세 스토리는 아래 ③ 섹션 (평가로 약점 진단 → 확장 → 재평가 검증)
- 카탈로그 임베딩: 가격·판매상태는 임베딩 입력에서 제외 → **가격이 바뀌어도 재임베딩 비용 0원**,
  임베딩 재사용 키는 입력 해시 단독 → 스냅샷 재발행 시 **임베딩 API 호출 0회**

### 리랭커 모델도 벤치마크로 선정

6개 비전 모델을 동일 조건(10 query × 후보 20건 전수 판정 = 200판정)으로 비교:

| 모델 | nDCG@10 | 판정 실패 | latency | 판단 |
|---|---:|---:|---:|---|
| **gpt-5.6-luna** (채택) | 0.634 | **0/200** | 6.5s | 실패 0, 검증된 품질 |
| gemma-4-26b (대안) | 0.641 | 0/200 | 5.5s | 동급 품질, 30% 저렴 |
| qwen3.7-flash | 0.626 | 2/200 | 28.7s | 내부 reasoning 과다로 느림 |
| gpt-5-nano | 0.523* | **131/200** | 19.7s | 판정 실패 다수, 탈락 |
| nova-lite-v1 | 0.499 | 0/200 | 2.4s | 빠르지만 baseline 이하 |

**슬라이드 포인트**
- "baseline 고정 → 변경 → 재측정" 사이클 강조 (평가 주도 개발)
- 파이프라인 5단계 플로우 다이어그램 (위 구조도 참고)
- "실패해도 추천은 죽지 않는다": VLM 강등 구조
- 데이터 깔때기: 수집 2,943 → 검수 통과 1,991 → TPO 확장 후 15,192건

## ③ 카탈로그 15k 확장과 TPO 평가 — "약점을 숫자로 진단하고, 개선도 숫자로 증명했다"

### 스토리: 평가 → 진단 → 확장 → 재평가의 완결된 사이클

"TPO(면접, 하객, 첫 출근 같은 상황)에 맞는 옷이 나오는가"는 nDCG 같은
순위 지표로는 잴 수 없습니다 — **모집단 자체가 상황과 어긋나면** 그 안에서
순위를 아무리 잘 매겨도 소용없기 때문. 그래서 사람 판정 평가를 새로 만들었습니다.

1. **TPO 평가셋 구축**: 24개 쿼리 (포멀/데일리/파티·데이트/운동/여행/계절,
   남녀·상하의 균형), 팀원이 웹 데모에서 추천 결과를 적합/부적합/모름으로 판정
2. **확장 전 baseline 고정** (8/5, 카탈로그 1,991건): 평가자 6명 × 24쿼리 × 10건
   = **판정 1,440건 전량 완료** → macro fit rate **0.772**
3. **약점이 정확히 드러남**: 운동·발표·여행은 0.96~0.98로 문제없는데,
   **포멀·격식 계열이 최하위** — 첫 출근 0.49, 겨울 데이트 0.50, 남성 면접 0.54.
   캐주얼 재고는 충분하지만 포멀 재고와 TPO 신호가 부족하다는 진단.
4. **처방 실행**: ① TPO 균형 수집 4일 (정규화 17,604건, READY 12,726 → 완화 정책
   적용 후 15,202건) ② 전 상품 **VLM TPO 태깅** (한국어 태그·캡션을 임베딩 문서에
   결합) ③ 전량 재임베딩 + 15,192건 EC2 배포 ④ `/rank`에 TPO 조건 반영
5. **같은 잣대로 재평가** (8/6, 평가자 7명 × 24쿼리 = **판정 1,680건**):

| | 2k baseline | 15k + TPO 태그 | Δ |
|---|---:|---:|---:|
| macro fit rate | 0.772 | **0.927** | **+0.155** |
| UNFIT 판정 수 | 308 | 121 | **−61%** |

포멀 클러스터가 목표대로 회복: **첫 출근 0.49→0.97, 남성 면접 0.54→0.99,
겨울 데이트 0.50→0.93**. 24개 쿼리 중 20개 개선, 하락 4개는 최대 −0.05 (잡음 수준).

**슬라이드 포인트**
- "지표가 없으면 만들었다": nDCG로 못 재는 실패 모드 → 사람 판정 평가 신설
- 막대 비교: 첫 출근 0.49→0.97 (가장 극적인 쿼리 3~4개만 골라서)
- macro 0.772 → 0.927 계단 차트 + "판정 3,120건(1,440+1,680)을 팀원이 직접"
- 진단→처방→검증 사이클 다이어그램 (평가 주도 개발의 확장판)

## ④ 트러블슈팅 하이라이트

발표에서 임팩트 있는 순서로 정리. 각 건은 "증상 → 원인 → 해결 → 교훈" 구조입니다.

### 1. VLM 판정이 조용히 전멸한 사건 (가장 극적인 사례)

- **증상**: 벤치마크에서 특정 모델 판정 실패 118~200/200. 그런데 에러 없이
  지표만 규칙 baseline과 정확히 일치 — 전량 fallback으로 강등되고 있었음.
- **원인**: OpenAI reasoning 계열 모델은 **숨은 reasoning 토큰이 max_tokens를 함께
  소진** → 응답이 `finish_reason: length` + 빈 내용으로 잘림. 토큰 절약을 위해
  max_tokens를 64로 줄인 것이 역효과.
- **해결**: 판정 상한 256 + `reasoning effort: low` 지정 → 실패 0.
- **교훈**: ① fallback이 있는 시스템은 실패가 "에러"가 아니라 "지표 열화"로만
  나타난다 → **실패 카운트를 반드시 별도 지표로 노출**. ② 토큰 절약 최적화는
  reasoning 모델에서 역효과가 날 수 있다.

### 2. 스냅샷 로드 실패가 타임아웃 폭풍으로 (15k 배포 직후 장애)

- **증상**: 15k 배포 직후 `/rank` 응답이 요청마다 수 초씩 지연 → 호출자(Spring)
  타임아웃 연쇄 발생.
- **원인**: 두 가지가 겹침. ① 백엔드 규약 변경으로 image_url이 절대 URL 대신
  **S3 객체 키**로 저장됐는데, 스냅샷 검증이 이를 거부해 인덱스 로드가 실패.
  ② 로더의 `lru_cache`는 **예외를 캐시하지 않아서**, 실패한 로드가 요청마다
  372MB JSON 재파싱을 반복 — 실패의 비용 자체가 장애가 됨.
- **해결**: 객체 키 형태 image_url 허용 + 로드 실패를 60초 backoff로 기억해
  즉시 규칙 기반 baseline으로 강등.
- **교훈**: ① 성공만 캐시하는 시스템은 실패가 반복 비용이 된다 — **실패 경로에도
  캐시/차단이 필요**. ② 파트 간 데이터 규약 변경은 소비자 쪽 검증 로직까지 함께 점검.

### 3. 게이트웨이는 알아서 정규화해주지 않는다

- reasoning effort를 하드코딩하자 이번엔 Gemma가 **reasoning 필드 자체를 거부**해
  197/200 실패. OpenRouter가 모델별 파라미터 차이를 흡수해줄 거라는 가정이 틀렸음.
- 해결: effort를 설정값으로 분리(빈 값 = 미전송)하고 모델과 세트로 관리.

### 4. 캐시 키 잠복 버그 — 1,991건 재과금될 뻔

- 임베딩 재사용 키가 `(product_id, 입력 해시)`였는데, DB를 옮기면 product_id가
  재발급되므로 **전량 캐시 미스 → 1,991건 전부 유료 재임베딩**될 뻔.
- 임베딩은 입력만의 순수 함수임을 확인하고 키를 **입력 해시 단독**으로 수정
  → EC2 스냅샷 재발행 시 **임베딩 API 호출 0회** 달성.
- 교훈: **캐시 키에는 결과를 결정하는 입력만 넣는다. 환경 종속 식별자 금지.**

### 5. 배포 인프라의 함정들 (EC2 배포 편)

- **Jenkins DooD 바인드 경로 착시**: compose는 Jenkins 컨테이너 안에서 돌지만
  바인드 마운트는 호스트 경로로 해석됨 → 인덱스 파일이 컨테이너에서 빈 디렉터리로
  보였던 원인. 실제 checkout은 Docker 볼륨 내부에 있었음.
- **SSH 터널 경유 DB 시드 타임아웃**: 터널 왕복지연 × 약 14,500 statement가 기본
  2분 초과 → 트랜잭션 롤백 안전성 확인 후 타임아웃 10분으로 재실행, 약 5분에 완료.
- **Windows 파일 잠금(WinError 5)**: 진행 확인용으로 체크포인트 파일을 여는 순간
  원자적 파일 교체와 경합해 빌드 전체가 사망 → 진행 확인은 파일 크기로만.

### 6. 병합 후 컴파일은 되는데 기동이 안 되는 의미 충돌

- dev 병합이 텍스트 충돌 없이 성공했지만, 상대 쪽 신규 코드가 우리가 non-null로
  강화한 컬럼 없이 데이터를 생성해 기동 시 제약 위반.
- 교훈: merge가 깨끗해도 스키마 강화 + 상대 신규 코드 조합은 기동 검증 필요.

**슬라이드 포인트**
- 1번 사례를 메인으로: "에러 로그가 아니라 지표가 baseline과 똑같아서 눈치챘다"
- 2번 사례: "실패도 캐시해야 한다" — fallback 설계의 숨은 비용 (실전 장애라 설득력 높음)
- 4번 사례: "캐시 키 한 줄 수정으로 재배포 비용 0원" (수치가 명확해서 전달력 좋음)

## ⑤ 지연(Latency) 개선 여정

### 추천 리랭크: 35초 → 9.5초 (판정 수는 4배로 늘리고도 3.7배 단축)

| 단계 | 조건 | latency |
|---|---|---:|
| 순차 판정 | 후보 5건, 판정 근거 문장 포함 | 35.1s |
| 병렬 8 + 점수만 출력 | 후보 5건 | 8.9s |
| 병렬 8 | 후보 20건 (3웨이브) | 21.4s |
| **병렬 20 (1웨이브)** | **후보 20건** | **9.5s** |

개선 수단 3가지:
1. **판정 병렬화** — 순차 → 동시 실행 (최종 20 동시, 웨이브 1회)
2. **출력 축소** — 판정 근거 문장 제거, 점수만 출력 (토큰 감소 = 응답시간 감소)
3. **웨이브 통합** — 후보 20건을 3번에 나눠 보내던 것을 1번에

남은 병목은 "가장 느린 판정 1건 + 쿼리 임베딩 1회"로, 추가 단축은 모델 교체
(gemma 전환 시 ~15% 추가 단축) 영역임을 분석으로 확인.

### 벡터 검색: 카탈로그 7.6배 확장에 대비한 선제 최적화 (250ms → 25ms)

카탈로그가 2k → 15k로 커지자 순수 파이썬 내적 루프가 병목 후보로 부상.
실측으로 확인 후 **numpy float64 행렬 연산**으로 교체했습니다.

| 케이스 | 전 (파이썬 루프) | 후 (numpy 행렬곱) |
|---|---:|---:|
| 최악 (성별 필터만, 15k 전량 내적) | 250ms | **25ms** |
| 일반 (카테고리+예산 필터) | 88ms | **13ms** |

- **품질 완전 동등을 증명하고 배포**: float64 유지 덕에 오프라인 평가
  (recall@K, nDCG@K, pairwise)가 쿼리별 지표까지 **소수점 끝자리 동일**
- 부수 효과: 검색이 GIL을 점유하는 시간이 1/10로 줄어 동시 요청 직렬화 문제 해소
- 스냅샷 포맷·API 계약·점수 의미 무변경 — 백엔드 영향 0

### 데모 체감 개선

- 파이프라인 진행 이벤트를 NDJSON 스트리밍으로 노출 → 데모 화면에 실시간
  타임라인 표시 (기다리는 9.5초 동안 어느 단계가 도는지 보임)

**슬라이드 포인트**
- 35.1 → 8.9 → 9.5(판정 4배) 계단 차트가 가장 직관적
- "판정 수를 4배 늘렸는데 시간은 그대로" 라는 카피 추천
- 벡터 검색: "카탈로그를 7.6배 키우고도 검색은 10배 빨라졌다" + "품질 지표는
  소수점 끝자리까지 동일함을 증명하고 배포" (평가 하네스가 있어서 가능했던 무위험 최적화)
