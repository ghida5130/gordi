# AI 이미지 모델 평가 프로세스 개선안

- 작성일: 2026-08-05
- 대상: GORDI 가상 피팅 이미지 생성 모델 선정·재평가
- 근거 데이터: 버전 관리된 1·2차 실제 Run 16개, pairwise 투표 933개
- 최종 선정 결과: 2차 평가 결과에 따라 `Nano Banana 2`를 최종 모델로 선정
- 현재 champion: `Nano Banana 2` (`google/gemini-3.1-flash-image`)
- 문서 상태: 다음 모델 평가부터 적용할 v3 제안

## 1. 목적

기존 1·2차 평가는 `Nano Banana 2`를 현재 서비스에 가장 적합한 주 모델로
선정하는 데 충분한 실무 근거를 만들었다. 특히 2차 결과는 평가자·시나리오 동일
가중과 leave-one-out 분석에서도 1위가 유지돼 최종 결정이 견고했다.

반면 평가가 끝난 뒤에야 순위 민감도, 독립 표본 단위, 미완주 세션 포함과 원본
데이터 변경 가능성을 확인했다. 이 문서는 현재 결정을 뒤집기 위한 것이 아니라,
다음 평가부터 같은 결론을 더 적은 해석 논쟁과 더 높은 재현성으로 만들기 위한
운영 규칙을 정의한다.

## 2. 재집계에서 확인한 핵심 사실

### 2.1 1차는 champion 선정이 아니라 screening으로 해석해야 한다

원 집계에서 1차 상위 3개는 GPT Image 2 68.4, Nano Banana 2 Lite 67.7,
Nano Banana 2 67.6으로 0.8점 안에 모였다. 한 평가자나 한 Run을 제외하면 1위가
세 모델 사이에서 바뀌었고, 평가자별 동일 가중에서는 FLUX.2 Max가 1위가 됐다.

따라서 1차의 성과는 정확한 1위를 찾은 것이 아니라 다음 네 모델을 상위 후보군으로
남긴 것이다. 하위 3개를 제거해 2차 비교 수를 Run당 21개에서 6개로 줄인 결정은
유효했다.

### 2.2 2차 champion은 여러 집계 방식에서 유지됐다

| 집계 방식 | Nano Banana 2 | 2위 | 차이 |
| --- | ---: | ---: | ---: |
| 원 집계 | 72.7 | GPT Image 2 52.5 | 20.2 |
| 평가자 동일 가중 | 72.7 | Lite 50.6 | 22.1 |
| 시나리오 동일 가중 | 70.4 | Lite 53.1 | 17.4 |
| 평가자 1명씩 제외 | 1위 유지 | - | 17.8~22.1 |
| Run 1개씩 제외 | 1위 유지 | - | 13.3~25.1 |

선호도와 품질 중 어느 한쪽의 가중치를 높여도 Nano Banana 2가 두 지표 모두
1위이므로 2차 champion은 바뀌지 않는다. 다만 2~4위 순서는 집계 방식에 따라
달라져 폴백 모델은 이번 순위를 그대로 사용하지 말고 별도 운영 평가로 선정해야
한다.

따라서 GORDI의 주 이미지 생성 모델은 2차 최종 집계를 근거로
`Nano Banana 2`로 최종 선정했다. 아래 개선 항목은 이 결정을 재개방하는 조건이
아니라, 차기 모델 재평가의 재현성과 통계적 신뢰도를 높이기 위한 후속 작업이다.

### 2.3 933표는 독립 표본 933개가 아니다

pairwise 투표는 같은 평가자가 한 Run에서 여러 모델 쌍을 연속 판단한 기록이다.
품질 점수도 동일 모델이 여러 쌍에 등장할 때 반복 입력됐다.

- 1차: 39개 `평가자 × Run` 세션, 이 중 38개 완주
- 2차: 33개 `평가자 × Run` 세션, 모두 완주
- 2차 모델별 품질 기록: 99개
- 2차 모델별 독립 군집 단위: 33개

평균 순위 계산에는 모든 기록을 사용할 수 있지만 신뢰구간, 유의성 검정과
부트스트랩은 `평가자 × Run` 단위로 묶어야 한다.

### 2.4 케이스와 평가자 배분이 완전히 균형적이지 않았다

1차 실제 Run 8개는 고유 시나리오 4개로 구성됐고 두 시나리오가 각각 3회
반복됐다. GPT Image 2는 두 Run에서 생성 실패해 다른 모델보다 평가된 시나리오와
비교 수가 적었다. 따라서 1차 시나리오 동일 가중 결과도 GPT Image 2는 네
시나리오 중 관측된 두 시나리오만 평균한 탐색적 수치로 해석해야 한다.

2차는 고유 시나리오 6개였지만 D2와 E3가 각각 두 번 포함됐고 E2는 빠졌으며,
대신 단일 의상 A1이 포함됐다. 평가자별 참여량도 달랐다. 원 집계는 참여가 많은
평가자와 중복 시나리오에 더 큰 가중치를 준다.

### 2.5 실패 원인 데이터가 구조화되지 않았다

2차 자유 메모는 198표 중 7개뿐이었다. 레퍼런스 인물 복제, 임의 신발 생성,
색상 변경, 넣어 입기와 소매 길이 불일치가 기록됐지만 발생률이나 모델별 분포를
계산할 수 없다.

### 2.6 최종 데이터가 마감 후에도 변경될 수 있었다

최종 선정 스냅샷은 933표였지만 데모가 계속 쓰기 가능해 2026-08-05에 1차
미완주 세션의 새 투표 4개가 작업 트리에 추가됐다. 문서 수치와 라이브 원본이
달라질 수 있으므로 의사결정 시점의 불변 스냅샷이 필요하다.

## 3. v3 평가 원칙

1. **목적을 먼저 고정한다.** 후보 제거용 screening과 champion 선정용
   validation을 같은 종료 기준으로 평가하지 않는다.
2. **프로토콜을 사전 등록한다.** 데이터셋, 모델 버전, 점수식, 표본 수, 제외
   규칙과 종료 조건을 첫 생성 전에 문서화한다.
3. **완주 세션만 공식 집계한다.** 진행 중 투표는 `DRAFT`, 모든 쌍 제출 후
   `COMPLETE`로 원자적으로 확정한다.
4. **평가자와 시나리오를 동일 가중한다.** 참여량이 많은 사람이나 중복 Run이
   결과를 지배하지 않게 한다.
5. **독립 단위를 명시한다.** 화면 클릭 수가 아니라 `평가자 × Run`을 통계
   단위로 사용한다.
6. **품질·속도·비용·안정성을 분리 보고한다.** 하나의 종합점수만으로 운영
   결정을 숨기지 않는다.
7. **champion과 fallback을 별도로 정한다.** fallback은 공급자 독립성, 장애
   유형, 비용과 전환 시간을 포함해 평가한다.

## 4. 권장 평가 설계

### 4.1 단계 A: 넓은 후보 screening

목적은 정확한 1위가 아니라 명백히 경쟁력이 낮은 후보를 저비용으로 제거하는
것이다.

| 항목 | 권장값 |
| --- | --- |
| 후보 수 | 6~10개 |
| 고유 시나리오 | 최소 6개 |
| 생성 반복 | 시나리오당 1 seed |
| 평가자 | 최소 3명, 동일 Run 집합 평가 |
| 후보 실패 처리 | 같은 모델만 1회 재시도, 계속 실패하면 해당 Run 전체를 공식 품질 집계에서 제외하고 안정성 지표에 실패 기록 |
| 통과 기준 | 종합순위뿐 아니라 핵심 품질 하한, 성공률과 비용 상한 충족 |
| 결과 | 3~4개 validation 후보 |

screening의 1~3위가 근소하면 순서를 확정하지 않고 동일 후보군으로 묶는다. 하위
제외 기준은 예를 들어 핵심 품질 평균 3.0 미만, `NEITHER` 비율 과다, 성공률
95% 미만처럼 사전에 정한다.

### 4.2 단계 B: champion validation

최종 단계는 실제 서비스 입력 분포와 실패 위험을 균형 있게 포함한다.

| 축 | 포함 조건 |
| --- | --- |
| 성별 | 여성·남성 균형 |
| 의상 구성 | 단일 상의, 단일 하의, 상·하의 조합 |
| 레퍼런스 | 상품 단독컷, 인물 착용컷 |
| 핏 | 타이트, 레귤러, 릴랙스/와이드 |
| 난이도 | 로고·그래픽, 레이어 경계, 짧은 소매·기장, 색상 민감 케이스 |

권장 최소 규모는 고유 시나리오 6개에 seed 2개를 적용한 12 Run, 평가자 5명이다.
후보 4개면 Run당 6쌍이므로 총 360개의 pairwise 투표가 생성된다. 모든 평가자가
동일 Run 집합을 완주하는 complete block을 기본으로 한다.

평가 부담이 크면 모든 사람이 일부 Run만 보는 balanced incomplete block을
사용하되, 각 Run의 평가자 수와 각 평가자의 Run 수를 동일하게 맞춘다.

### 4.3 한 번만 매기는 품질 점수와 pairwise 선호를 분리한다

현재 화면은 같은 후보가 다른 쌍에 등장할 때 품질 점수를 반복 입력한다. v3에서는
다음 두 단계를 분리한다.

1. 각 Run의 후보 이미지를 무작위 순서로 한 번씩 보여주고 모델당 품질 네 항목과
   실패 태그를 한 번 저장한다.
2. 이후 모델명을 숨긴 pairwise 선호만 평가한다.

이렇게 하면 모델별 품질 표본 수가 실제 `평가자 × Run` 수와 일치하고, 반복
입력 피로와 앞선 비교 점수 복사 문제를 줄일 수 있다.

### 4.4 실패 태그를 구조화한다

| 태그 | 의미 |
| --- | --- |
| `SOURCE_PERSON_LEAK` | 의상 레퍼런스의 얼굴·체형·포즈를 복제 |
| `BODY_DRIFT` | PERSON BASE 체형·비율 변경 |
| `GARMENT_IDENTITY_DRIFT` | 로고·그래픽·재질·구조 변경 |
| `COLOR_DRIFT` | 의류 핵심 색상 변경 |
| `FIT_MISMATCH` | 선택 사이즈·핏·기장 지시 불일치 |
| `EXTRA_ITEM` | 신발·액세서리·다른 의상 임의 생성 |
| `MISSING_ITEM` | 요청한 의상 누락 |
| `LAYERING_ERROR` | 넣어 입기, 겹침, 허리선·소매 경계 오류 |
| `ANATOMY_ARTIFACT` | 손·발·신체 결함 |

다중 선택을 허용하고 `NONE`을 명시적으로 제공한다. 자유 메모는 태그를 설명하는
보조 필드로 둔다.

## 5. 집계와 통계 규칙

### 5.1 공식 집계 단위

- pairwise 선호: 승/무/패/둘 다 아님을 원시 기록으로 보존
- 품질: `평가자 × Run × 모델`당 1개 점수
- 모델 성능: 평가자 동일 가중 후 시나리오 동일 가중
- 불확실성: `평가자 × Run` 군집 부트스트랩 95% 신뢰구간
- Run 반복: 같은 시나리오의 seed는 먼저 시나리오 내부에서 평균

### 5.2 점수식

현재의 `선호도 60% + 품질 40%`는 유지할 수 있지만 v3 프로토콜에 사전
등록한다. 동시에 다음 지표를 별도 표로 반드시 공개한다.

- pairwise 선호도
- 품질 네 항목과 핵심 하한
- `NEITHER` 비율
- 실패 태그별 발생률
- 성공률, 재시도율
- p50·p95 지연시간
- 성공당 비용과 월간 예상 비용

`NEITHER`는 무승부로 합치지 않는다. 두 후보가 모두 서비스 불가였다는 절대 실패
신호로 별도 집계한다.

### 5.3 champion 종료 조건

아래 조건을 모두 충족할 때만 `FINAL PICK`을 표시한다.

1. 계획한 Run과 평가자 세션이 100% 완료됐다.
2. 원 집계, 평가자 동일 가중, 시나리오 동일 가중에서 같은 모델이 1위다.
3. 평가자 leave-one-out과 Run leave-one-out에서 1위가 바뀌지 않는다.
4. 1위와 2위의 종합점수 차이가 5점 이상이고 군집 부트스트랩 하한이 0보다 크다.
5. 의류 보존과 체형 보존이 각각 사전 정의한 품질 하한을 충족한다.
6. 성공률·p95 지연시간·성공당 비용이 운영 상한을 충족한다.

조건을 충족하지 않으면 `CURRENT LEADER`로 표시하고 케이스나 평가자를 추가한다.

## 6. 데이터와 재현성

평가 종료 시 다음 구조로 스냅샷을 만든다.

```text
ai/eval/snapshots/<evaluation-id>/
  protocol.json
  dataset-manifest.json
  model-manifest.json
  runs/
  votes.jsonl
  aggregate.json
  sensitivity.json
  SHA256SUMS
```

필수 메타데이터는 다음과 같다.

- `evaluation_id`, `evaluation_round`, `protocol_version`
- `dataset_version`, 케이스 ID, 원본 이미지 해시
- 공급자, 정확한 모델 ID·revision, 라우팅 정보
- 프롬프트·핏 규칙 버전과 최종 프롬프트 해시
- seed 또는 공급자가 제공하는 재현 식별자
- 평가자 익명 ID, `session_status`, 시작·완료 시각
- 요청 ID, 시도 번호, 성공·실패, 지연시간, 요청 단위 비용
- 집계 코드 commit SHA와 snapshot cutoff

스냅샷 생성 후 원본은 읽기 전용으로 잠그고 후속 투표는 새 `evaluation_id`에
저장한다. 회고 문서는 라이브 디렉터리가 아니라 해당 snapshot 경로를 참조한다.

## 7. 운영 적용

### 7.1 champion 운영

현재 `Nano Banana 2` 선택은 유지한다. 모델 revision, 프롬프트 버전과 핏 규칙을
프로덕션 결과에 저장하고 대표 회귀 세트에서 주기적으로 품질을 확인한다.

### 7.2 fallback 별도 평가

2차에서 2~4위 순서는 가중 방식에 따라 바뀌었다. 따라서 fallback은 단순히
2차 종합 2위를 택하지 않는다.

- Google 장애 시 사용할 수 있도록 공급자 독립성 확보
- 타임아웃, 429, 5xx, 안전 필터별 전환 가능성 검증
- 낮은 비용과 짧은 p95 지연시간
- champion 대비 품질 손실 상한
- 전환 시 프롬프트·입력 형식 호환성

### 7.3 champion–challenger 재평가

모델 revision 변경, 품질 회귀 경보, 비용 20% 이상 변화 또는 분기마다 challenger
1~2개를 동일한 고정 회귀 세트로 평가한다. 새 모델이 종료 조건을 충족할 때만
champion을 교체한다.

## 8. 구현 우선순위

| 우선순위 | 작업 | 완료 조건 |
| --- | --- | --- |
| P0 | 평가 세션 상태 도입 | `DRAFT` 투표가 공식 집계에서 제외되고 `COMPLETE`가 원자적으로 확정됨 |
| P0 | 불변 스냅샷 생성기 | protocol·manifest·runs·votes·aggregate·해시를 한 디렉터리에 생성 |
| P0 | 집계 가중 수정 | 평가자 동일 가중과 시나리오 동일 가중을 기본 결과에 표시 |
| P0 | 민감도 자동화 | evaluator/run leave-one-out 결과와 최소 격차 자동 계산 |
| P1 | 품질 평가 화면 분리 | 후보당 한 번만 품질 점수를 입력하고 pairwise에서는 선호만 선택 |
| P1 | 구조화 실패 태그 | 모델·시나리오별 실패율을 대시보드에서 확인 가능 |
| P1 | 요청 단위 비용 원장 | OpenRouter와 BYOK 직접 청구를 동일 request ID로 연결 |
| P1 | 군집 부트스트랩 | `평가자 × Run` 기준 95% 신뢰구간 제공 |
| P2 | balanced block 배정 | 평가자별 Run 수와 Run별 평가자 수를 동일하게 자동 배정 |
| P2 | champion–challenger 자동화 | 고정 회귀 세트 실행부터 교체 보고서까지 반복 가능 |

## 9. 완료 정의

다음 평가에서 아래 질문에 모두 파일과 수치로 답할 수 있으면 개선이 완료된 것으로
본다.

1. 어떤 데이터셋·모델 revision·프롬프트로 생성했는가?
2. 몇 개의 완주 `평가자 × Run` 단위가 공식 집계에 포함됐는가?
3. 평가자와 시나리오를 동일 가중해도 winner가 같은가?
4. 한 평가자나 한 Run을 제외해도 winner가 같은가?
5. 품질 격차의 군집 신뢰구간은 얼마인가?
6. 어떤 실패 유형이 모델별로 얼마나 발생했는가?
7. 성공률, p95 지연시간과 성공당 실제 비용은 얼마인가?
8. 결정 당시 원본과 집계 결과를 동일하게 다시 생성할 수 있는가?
