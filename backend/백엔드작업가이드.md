# 백엔드 작업 가이드

## 1. 문서 목적

이 문서는 `backend` 모듈의 현재 패키지 구조와 각 계층의 책임을 설명하고, 새로운 REST API를 구현할 때 어떤 파일을 어느 패키지에 생성해야 하는지 안내한다.

현재 프로젝트는 `com.ssafy.backend` 아래에서 **계층형 패키지 구조(Package by Layer)** 를 사용한다. DTO만 API 도메인별 하위 패키지로 나누며, 외부 시스템 연동 코드는 `infra`에 둔다.

모든 Spring Bean과 JPA Entity는 `BackendApplication`의 기본 컴포넌트 스캔 범위인 `com.ssafy.backend` 아래에 생성해야 한다.

## 3. 패키지별 책임

### 3.1 `common`

여러 API에서 공통으로 사용하는 응답, 예외, 시간 관련 코드를 둔다.

- `common.response`: 성공 응답 공통 형식
- `common.error`: 오류 코드, 공통 예외, 예외 응답 변환
- `common.time`: 애플리케이션 공통 시간대

Controller의 성공 응답은 기본적으로 `ApiResponse.success(data)`로 감싼다.

예측 가능한 비즈니스 오류는 Service에서 `ApiException`으로 발생시키고, `CustomControllerAdvice`가 공통 `ErrorResponse`로 변환한다.

### 3.2 `config`

Spring Bean 설정, 보안 설정, 외부 클라이언트 설정, 기능 정책값을 둔다.

- `SecurityConfig`: Spring Security 설정
- `WebSocketConfig`: WebSocket 설정
- `AiClientConfig`: 외부 AI 서버 호출용 Bean 설정
- `RecommendationPolicy`: 추천 정책 프로퍼티
- `config.enums`: 추천 API의 선택값, 상태값, 사유 코드

Java 예약어인 `enum`은 패키지명으로 사용할 수 없으므로 패키지 이름은 `enums`를 사용한다.

`ErrorCode`처럼 오류 처리 계층 자체를 표현하는 enum은 `common.error`, `RoomEventType`처럼 특정 프로토콜에 종속된 enum은 소유 패키지에 둘 수 있다. API의 공통 선택값이나 정책 상태 enum을 새로 만들 때는 기본적으로 `config.enums`를 사용한다.

### 3.3 `controller`

HTTP 요청과 응답만 담당한다.

Controller에서 수행할 일:

- URL과 HTTP Method 선언
- Header, Path Variable, Query Parameter, Request Body 수신
- `@Valid`를 이용한 요청 DTO 검증
- 인증 객체에서 필요한 사용자 식별 정보 추출
- Service 호출
- `ApiResponse` 및 적절한 HTTP 상태 반환

Controller에서 하지 않을 일:

- Repository 직접 호출
- Entity 직접 저장
- 복잡한 비즈니스 규칙 처리
- 외부 API 직접 호출
- 오류 응답 JSON 직접 생성

### 3.4 `domain`

JPA Entity와 핵심 도메인 모델을 둔다.

- 데이터베이스 테이블과 매핑되는 클래스는 `@Entity`를 사용한다.
- 연관관계, 컬럼 제약, 생성 시 기본값처럼 데이터 모델에 속하는 규칙을 정의한다.
- Controller, Service, DTO에 의존하지 않는다.
- API 응답에 Entity를 직접 반환하지 않는다.

### 3.5 `dto`

API 입출력 및 계층 간 전달 객체를 둔다.

DTO는 반드시 API 도메인별 하위 패키지에 생성한다.

```text
dto
├── auth
├── recommendation
├── room
└── users
```

새 API 도메인이 추가되면 최상위 `dto`에 파일을 만들지 않고 `dto.<api-domain>` 패키지를 먼저 만든다.

예:

```text
dto
└── order
    ├── OrderCreateRequest
    ├── OrderUpdateRequest
    └── OrderResponse
```

요청 DTO에는 필드 단위 형식 검증을 선언한다.

- 필수값: `@NotNull`, `@NotBlank`, `@NotEmpty`
- 숫자 범위: `@Positive`, `@PositiveOrZero`, `@Min`, `@Max`
- 문자열/컬렉션 크기: `@Size`
- 중첩 DTO 검증: `@Valid`

요청 DTO의 두 필드를 비교해야 하는 규칙이나 데이터베이스 조회가 필요한 검증은 Service에서 처리한다.

### 3.6 `filter`

HTTP 요청이 Controller에 도달하기 전에 수행되는 인증·인가 필터를 둔다.

- JWT 검증
- 로그인 요청 처리
- SecurityContext 구성

필터에서 오류 응답이 필요하면 JSON 문자열을 직접 만들지 않고 `ApiErrorResponseWriter`를 사용한다.

### 3.7 `handler`

Spring Security 인증 성공·실패, 로그아웃처럼 보안 흐름의 후처리를 담당한다.

일반 REST API의 비즈니스 로직은 Handler에 작성하지 않는다.

### 3.8 `infra`

외부 시스템과 통신하는 구현체를 둔다.

예:

- FastAPI/AI 서버 호출
- 외부 결제 API 호출
- 외부 스토리지 또는 메시징 시스템 호출

외부 호출의 URL, Header, 직렬화, 타임아웃, 외부 예외 변환은 `infra`가 담당한다. Service는 외부 통신의 세부 구현을 알지 않고 Infra Client를 주입받아 사용한다.

외부 통신 실패는 외부 응답을 그대로 노출하지 않고 프로젝트의 `ApiException`과 `ErrorCode`로 변환한다.

### 3.9 `repository`

Spring Data JPA 기반 데이터 접근을 담당한다.

- `JpaRepository<Entity, IdType>` 상속
- 단순 조회는 메서드 이름 기반 쿼리 사용
- Fetch Join이나 복잡한 조건은 `@Query` 사용
- 반환 타입은 Entity, `Optional<Entity>`, Entity 컬렉션 또는 명확한 Projection 사용

Repository는 DTO나 Service에 의존하지 않는다.

### 3.10 `service`

API의 애플리케이션 흐름과 비즈니스 규칙을 담당한다.

- Entity 조회와 생성
- 권한 및 상태 검증
- 여러 Repository 작업 조합
- Infra Client 호출
- DTO 변환
- 트랜잭션 경계 설정
- 멱등성 처리

쓰기 작업은 `@Transactional`, 조회 전용 작업은 가능한 경우 `@Transactional(readOnly = true)`를 사용한다.

Service에서 `ResponseEntity`, HTTP Status 같은 웹 계층 타입을 반환하지 않는다.

### 3.11 `util`

특정 계층에 속하지 않는 재사용 가능한 무상태 도우미를 둔다.

예:

- 쿠키 생성
- JWT 파싱
- 방 토큰 생성

비즈니스 상태를 저장하거나 Repository를 조합하는 코드는 Util이 아니라 Service에 둔다.

### 3.12 `websocket`

STOMP/WebSocket 인증, 이벤트 발행, 세션 Principal, 실시간 메시지 타입을 둔다.

REST API용 Controller와 DTO를 WebSocket 프로토콜 코드에 직접 섞지 않는다. 공통 도메인 로직이 필요하면 Service를 호출한다.

## 4. 권장 의존 방향

기본 호출 흐름은 다음과 같다.

```text
HTTP Request
    ↓
Controller
    ↓
Service
    ├── Repository
    │       ↓
    │     Domain
    └── Infra Client
            ↓
       External System
```

DTO와 공통 코드는 필요한 계층에서 사용한다.

```text
Controller ──→ DTO
Service    ──→ DTO, Domain, Repository, Infra, Common
Repository ──→ Domain
Infra      ──→ 외부 연동 DTO, Common
```

다음과 같은 역방향 의존은 만들지 않는다.

```text
Repository ─X→ Service
Domain     ─X→ Service 또는 Controller
Service    ─X→ Controller
Infra      ─X→ Controller
```

Service끼리 서로 양방향으로 주입하면 순환 참조가 발생할 수 있다. 공통 로직은 별도 Service 또는 정책 객체로 분리하고 의존 방향을 한쪽으로 유지한다.

## 5. 신규 API 구현 절차

아래 순서는 데이터베이스를 사용하는 일반적인 REST API 기준이다. 조회 전용 API이거나 외부 API를 사용하지 않는 경우 불필요한 단계는 생략한다.

### 5.1 API 도메인과 URL 결정

먼저 기존 API와 겹치지 않는 도메인명과 URL을 결정한다.

```text
도메인: order
기본 URL: /api/v1/orders
DTO 패키지: com.ssafy.backend.dto.order
```

기존 도메인을 확장할 때는 새로운 DTO 패키지를 만들지 않고 기존 패키지를 사용한다.

### 5.2 요청·응답 DTO 생성

생성 위치:

```text
src/main/java/com/ssafy/backend/dto/<api-domain>
```

예:

```java
package com.ssafy.backend.dto.order;

import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Positive;

public record OrderCreateRequest(
        @NotNull Long productId,
        @Positive int quantity
) {
}
```

```java
package com.ssafy.backend.dto.order;

public record OrderResponse(
        Long orderId,
        String status
) {
}
```

규칙:

- Entity를 Request Body로 직접 받지 않는다.
- Entity를 API 응답으로 직접 반환하지 않는다.
- 요청과 응답 DTO를 분리한다.
- API에 필요하지 않은 내부 필드는 DTO에 노출하지 않는다.
- 같은 API 도메인의 DTO는 같은 하위 패키지에 둔다.
- 새 DTO를 `com.ssafy.backend.dto` 바로 아래에 만들지 않는다.

현재 코드에는 `DTO` 접미사를 사용하는 패키지와 사용하지 않는 패키지가 함께 존재한다. 기존 도메인을 수정할 때는 해당 패키지의 명명 방식을 따르고, 새로운 도메인 안에서는 한 가지 방식을 일관되게 사용한다.

### 5.3 Entity 생성 또는 수정

영속 데이터가 필요하면 `domain`에 Entity를 생성한다.

```text
src/main/java/com/ssafy/backend/domain/Order.java
```

예:

```java
package com.ssafy.backend.domain;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import lombok.AccessLevel;
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;

@Entity
@Getter
@Builder
@NoArgsConstructor(access = AccessLevel.PROTECTED)
@AllArgsConstructor
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
}
```

Entity 작성 시 확인할 항목:

- 테이블명과 컬럼명
- `nullable`, `length`, `unique` 제약
- 연관관계의 Fetch Type
- 삭제 정책과 생명주기
- 생성·수정 시간
- 상태 변경 메서드

API에서 사용하는 선택값이나 상태 enum은 `config.enums`에 생성한다.

```text
src/main/java/com/ssafy/backend/config/enums/OrderStatus.java
```

### 5.4 Repository 생성

생성 위치:

```text
src/main/java/com/ssafy/backend/repository/OrderRepository.java
```

예:

```java
package com.ssafy.backend.repository;

import com.ssafy.backend.domain.Order;
import org.springframework.data.jpa.repository.JpaRepository;

import java.util.Optional;

public interface OrderRepository extends JpaRepository<Order, Long> {

    Optional<Order> findByIdAndUserId(Long orderId, Long userId);
}
```

`@Repository`는 Spring Data Repository 인터페이스에 필수는 아니다.

연관 Entity를 응답 변환 과정에서 사용한다면 N+1 또는 Lazy Loading 문제가 생기지 않도록 Fetch Join이나 EntityGraph 적용을 검토한다.

### 5.5 외부 시스템 Client 생성

외부 API를 호출하는 경우에만 `infra`에 Client를 생성한다.

```text
src/main/java/com/ssafy/backend/infra/OrderPaymentClient.java
```

예:

```java
package com.ssafy.backend.infra;

import org.springframework.stereotype.Component;

@Component
public class OrderPaymentClient {

    public void requestPayment(Long orderId) {
        // 외부 결제 API 호출
    }
}
```

필요한 `RestClient`, URL, Timeout Bean은 `config`에서 구성한다.

### 5.6 Service 생성

생성 위치:

```text
src/main/java/com/ssafy/backend/service/OrderService.java
```

예:

```java
package com.ssafy.backend.service;

import com.ssafy.backend.domain.Order;
import com.ssafy.backend.dto.order.OrderCreateRequest;
import com.ssafy.backend.dto.order.OrderResponse;
import com.ssafy.backend.repository.OrderRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }

    @Transactional
    public OrderResponse create(OrderCreateRequest request) {
        Order order = orderRepository.save(Order.builder().build());
        return new OrderResponse(order.getId(), "CREATED");
    }
}
```

Service 작성 시 확인할 항목:

- 현재 사용자에게 작업 권한이 있는가?
- 대상 Entity가 존재하는가?
- 현재 상태에서 요청한 동작이 가능한가?
- 중복 요청을 어떻게 처리할 것인가?
- 한 트랜잭션 안에서 처리해야 하는 범위는 어디까지인가?
- 외부 API 실패를 어떤 `ErrorCode`로 변환할 것인가?

### 5.7 Controller 생성

생성 위치:

```text
src/main/java/com/ssafy/backend/controller/OrderController.java
```

예:

```java
package com.ssafy.backend.controller;

import com.ssafy.backend.common.response.ApiResponse;
import com.ssafy.backend.dto.order.OrderCreateRequest;
import com.ssafy.backend.dto.order.OrderResponse;
import com.ssafy.backend.service.OrderService;
import jakarta.validation.Valid;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
@RequestMapping("/api/v1/orders")
public class OrderController {

    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping
    public ResponseEntity<ApiResponse<OrderResponse>> create(
            @Valid @RequestBody OrderCreateRequest request
    ) {
        OrderResponse response = orderService.create(request);
        return ResponseEntity
                .status(HttpStatus.CREATED)
                .body(ApiResponse.success(response));
    }
}
```

HTTP 상태 기준:

| 상황 | 상태 | 반환 방식 |
|---|---:|---|
| 일반 조회·수정 성공 | `200 OK` | `ApiResponse.success(data)` |
| 리소스 생성 성공 | `201 Created` | `ResponseEntity.status(CREATED)` |
| 비동기 작업 접수 | `202 Accepted` | `ResponseEntity.status(ACCEPTED)` |
| 성공했지만 응답 본문 없음 | `204 No Content` | `ResponseEntity.noContent()` |

### 5.8 오류 코드 추가

기존 `ErrorCode`에 적절한 오류가 없다면 새 코드를 추가한다.

```text
src/main/java/com/ssafy/backend/common/error/ErrorCode.java
```

Service에서는 다음과 같이 사용한다.

```java
throw new ApiException(
        ErrorCode.RESOURCE_NOT_FOUND,
        Map.of("orderId", orderId)
);
```

규칙:

- Controller에서 오류 응답을 직접 만들지 않는다.
- 예상 가능한 오류에 일반 `RuntimeException`을 사용하지 않는다.
- 토큰, 비밀번호, API Key, SQL, 외부 서비스의 원문 오류를 응답에 포함하지 않는다.
- `details`에는 클라이언트가 오류를 수정하는 데 필요한 안전한 정보만 넣는다.

### 5.9 보안 설정 확인

새 Endpoint를 추가하면 `SecurityConfig`에서 다음을 확인한다.

- 인증이 필요한가?
- 비회원 접근이 가능한가?
- 역할 기반 권한이 필요한가?
- CORS 또는 CSRF 설정에 영향이 있는가?

인증이 필요한 API는 인증되지 않은 사용자를 Service 로직까지 통과시키지 않는다.

### 5.10 테스트 생성

테스트 패키지는 운영 코드의 패키지를 가능한 한 동일하게 맞춘다.

```text
src/test/java/com/ssafy/backend
├── controller
│   └── OrderControllerTest.java
├── dto
│   └── order
│       └── OrderCreateRequestTest.java
└── service
    └── OrderServiceTest.java
```

권장 테스트 범위:

- DTO Validation
- Service 정상 흐름
- 존재하지 않는 리소스
- 권한 없음
- 상태 충돌
- 중복·멱등 요청
- Repository 쿼리
- 외부 시스템 실패 변환
- Controller HTTP 상태와 응답 형식

Service 단위 테스트는 Mockito로 Repository와 Infra Client를 Mock 처리한다. Spring Context가 필요한 통합 테스트는 실제 MySQL에 의존하지 않도록 H2 테스트 DB 설정을 명시한다.

Windows:

```powershell
.\gradlew.bat test
```

macOS/Linux:

```bash
./gradlew test
```

## 6. API 구현 파일 배치 예시

새로운 `order` API를 구현한다면 최소 구조는 다음과 같다.

```text
com.ssafy.backend
├── config
│   └── enums
│       └── OrderStatus.java
├── controller
│   └── OrderController.java
├── domain
│   └── Order.java
├── dto
│   └── order
│       ├── OrderCreateRequest.java
│       └── OrderResponse.java
├── infra
│   └── OrderPaymentClient.java       # 외부 결제 호출이 있을 때만 생성
├── repository
│   └── OrderRepository.java
└── service
    └── OrderService.java

src/test/java/com/ssafy/backend
├── controller
│   └── OrderControllerTest.java
├── dto
│   └── order
│       └── OrderCreateRequestTest.java
└── service
    └── OrderServiceTest.java
```

조회 전용 API라면 새 Entity나 Repository가 필요하지 않을 수 있다. 외부 호출이 없다면 Infra Client도 만들지 않는다. 필요한 계층만 생성하되, 해당 책임을 다른 계층에 섞지 않는다.

## 7. 작업 완료 체크리스트

- [ ] 모든 클래스가 `com.ssafy.backend` 아래에 있는가?
- [ ] Controller가 Repository 또는 Infra Client를 직접 호출하지 않는가?
- [ ] 비즈니스 로직과 트랜잭션이 Service에 있는가?
- [ ] Entity가 API 요청·응답으로 직접 노출되지 않는가?
- [ ] DTO가 `dto.<api-domain>` 패키지에 있는가?
- [ ] 최상위 `dto`에 DTO 파일을 생성하지 않았는가?
- [ ] API 선택값·상태 enum이 적절한 책임 패키지에 있는가?
- [ ] 외부 시스템 호출 코드가 `infra`에 있는가?
- [ ] 요청 DTO에 `@Valid`와 Validation Annotation을 적용했는가?
- [ ] 예상 가능한 오류가 `ApiException`과 `ErrorCode`로 처리되는가?
- [ ] 성공 응답이 `ApiResponse.success(data)` 형식을 따르는가?
- [ ] 생성·접수·본문 없음 응답에 올바른 HTTP 상태를 사용했는가?
- [ ] 쓰기와 조회 트랜잭션 범위를 구분했는가?
- [ ] Repository 쿼리의 N+1 및 Lazy Loading 문제를 검토했는가?
- [ ] 새 Endpoint의 Security 설정을 확인했는가?
- [ ] 운영 코드와 대응하는 테스트를 추가했는가?
- [ ] 전체 테스트가 통과하는가?
