## 2. Kakao Developers

### 2.1 사용 목적

Spring Security OAuth2 Client를 이용한 카카오 소셜 로그인에 사용한다. Frontend는 다음 Backend 로그인 시작 경로로 사용자를 이동시킨다.

```text
/api/v1/oauth2/authorization/kakao
```

Backend는 카카오에서 전달한 인증 코드를 다음 Callback 경로에서 처리한다.

```text
/api/v1/login/oauth2/code/kakao
```

### 2.2 가입 및 애플리케이션 생성

1. [Kakao Developers](https://developers.kakao.com/)에 Kakao 계정으로 로그인한다.
2. 애플리케이션 관리 화면에서 프로젝트용 애플리케이션을 생성한다.
3. 앱의 플랫폼 키에서 **REST API Key**를 확인한다.
4. REST API Key의 Client Secret을 생성하고 활성화한다.
5. Kakao Login 기능을 활성화한다.
6. 동의 항목에서 닉네임을 사용할 수 있도록 설정한다.
7. 로컬 및 운영 Redirect URI를 등록한다.

공식 참고 문서: [Kakao Login REST API](https://developers.kakao.com/docs/en/kakaologin/rest-api)

### 2.3 프로젝트에 필요한 값

| Kakao 설정 | 프로젝트 환경 변수 | 비고 |
| --- | --- | --- |
| REST API Key | `KAKAO_CLIENT_ID` | JavaScript Key나 Admin Key가 아님 |
| Client Secret | `KAKAO_CLIENT_SECRET` | 서버 전용, Frontend 노출 금지 |
| 로그인 성공 후 Frontend 주소 | `OAUTH2_REDIRECT_URL` | 예: `https://<서비스 도메인>/oauth/callback` |
| 로그인 실패 후 Frontend 주소 | `OAUTH2_FAILURE_REDIRECT_URL` | 예: `https://<서비스 도메인>/login?error=oauth` |

루트 `.env` 설정 예시는 다음과 같다.

```env
KAKAO_CLIENT_ID=<Kakao REST API Key>
KAKAO_CLIENT_SECRET=<Kakao Client Secret>
OAUTH2_REDIRECT_URL=https://<서비스 도메인>/oauth/callback
OAUTH2_FAILURE_REDIRECT_URL=https://<서비스 도메인>/login?error=oauth
```

### 2.4 Redirect URI

Kakao Developers에 등록할 Redirect URI는 Spring Security가 인증 코드를 받는 Backend 주소여야 한다. Kakao에 등록한 값과 실제 요청의 `redirect_uri`가 정확히 일치하지 않으면 로그인이 실패한다.

```text
# 로컬 Docker/Nginx 환경
http://localhost/api/v1/login/oauth2/code/kakao

# 운영 환경
https://<서비스 도메인>/api/v1/login/oauth2/code/kakao
```

Frontend의 `/oauth/callback`은 Kakao에 등록하는 Redirect URI가 아니라 Backend가 로그인 처리를 마친 뒤 사용자를 보내는 최종 화면이다.

### 2.5 동의 항목 및 플랫폼 설정

- 현재 Spring 설정 Scope: `profile_nickname`
- Backend는 사용자 식별자 `id`와 닉네임을 사용한다.
- 이메일이 응답에 있으면 사용하지만, 없으면 `kakao_<providerId>@social.local` 형식의 대체 이메일을 만든다.
- 운영 도메인과 로컬 도메인을 Web 플랫폼 사이트 도메인에 등록한다.
- 운영 전 앱 이름, 아이콘, 사업자·개인정보처리방침 등 Kakao 검수 요구 항목을 확인한다.

## 3. OpenRouter

### 3.1 사용 목적

OpenRouter는 다음 AI 기능의 API Gateway로 사용한다.

| 기능 | 기본 모델 또는 Endpoint |
| --- | --- |
| 상품 카탈로그 임베딩 | `google/gemini-embedding-2`, 768차원 |
| 추천 VLM 재정렬 | `openai/gpt-5.6-luna` |
| 가상 착장 이미지 생성 | `google/gemini-3.1-flash-image` |
| 임베딩 Endpoint | `https://openrouter.ai/api/v1/embeddings` |
| VLM 및 이미지 Endpoint | `https://openrouter.ai/api/v1/chat/completions` |

모델 이름과 제공 여부는 변경될 수 있으므로 인수인계 시점에 OpenRouter 모델 목록과 팀 계정의 접근 가능 여부를 다시 확인한다.

### 3.2 가입 및 API Key 생성

1. [OpenRouter](https://openrouter.ai/)에 로그인한다.
2. 결제 수단 또는 사용할 Credit을 등록한다.
3. API Keys 화면에서 프로젝트 전용 API Key를 생성한다.
4. 키 이름에는 용도를 명시한다. 예: `gordi-prod-ai`.
5. 예상하지 못한 과금을 막기 위해 가능한 경우 Key별 사용 한도를 설정한다.
6. 발급 직후 한 번만 표시되는 Key를 Jenkins의 `ai-env-file`에 저장한다.

공식 참고 문서: [OpenRouter Quickstart](https://openrouter.ai/docs/quickstart), [API Key 관리](https://openrouter.ai/docs/guides/overview/auth/management-api-keys)

> 일반 AI 요청에는 추론용 API Key를 사용한다. 키를 생성·관리하는 Management API Key와 혼동하지 않는다.

### 3.3 프로젝트 설정

`ai/.env`에 다음 값을 설정한다.

```env
OPENROUTER_API_KEY=<OpenRouter inference API key>
OPENROUTER_EMBEDDING_MODEL=google/gemini-embedding-2
OPENROUTER_EMBEDDING_DIMENSIONS=768
OPENROUTER_EMBEDDING_ENDPOINT=https://openrouter.ai/api/v1/embeddings
OPENROUTER_PROVIDER_ORDER=google-vertex
OPENROUTER_ALLOW_FALLBACKS=false
OPENROUTER_HTTP_REFERER=https://<서비스 도메인>
OPENROUTER_APP_TITLE=Gordi AI

RECOMMENDATION_VLM_MODEL=openai/gpt-5.6-luna
RECOMMENDATION_VLM_ENDPOINT=https://openrouter.ai/api/v1/chat/completions
RECOMMENDATION_VLM_API_KEY=
RECOMMENDATION_VLM_TIMEOUT_SECONDS=20

TRYON_IMAGE_MODEL=google/gemini-3.1-flash-image
TRYON_GENERATION_TIMEOUT_SECONDS=180
```

`RECOMMENDATION_VLM_API_KEY`가 비어 있으면 공통 `OPENROUTER_API_KEY`를 사용한다.

### 3.4 과금 및 운영 주의사항

- 임베딩 생성, 검색 Query 임베딩, VLM 재정렬, 이미지 생성은 각각 비용이 발생할 수 있다.
- 인덱스 전체 재생성 전에 소량의 샘플로 모델, 차원, 응답 형식을 검증한다.
- `google-vertex` Provider 고정 설정과 Fallback 비활성화 설정을 유지할 경우 해당 Provider 장애가 전체 요청 실패로 이어질 수 있다.
- API Key를 Frontend 환경 변수나 브라우저 코드에 넣지 않는다.
- Key가 노출되면 즉시 폐기하고 새 Key를 Jenkins Credential에 등록한 뒤 AI 컨테이너를 재생성한다.
- OpenRouter의 사용량 및 결제 알림을 운영 담당자 이메일로 설정한다.

### 4.1 사용하는 AWS 서비스

| AWS 서비스 | 사용 목적 | 저장소에서 확인한 값 |
| --- | --- | --- |
| EC2 | Docker, Jenkins, 애플리케이션 운영 | 정확한 Instance ID와 접속 주소는 저장소에 없음 |
| S3 | 상품 이미지 및 가상 착장 결과 저장 | 버킷 `gordi-app-bucket` 사용 이력 |

| IAM | EC2와 애플리케이션의 AWS 권한 관리 | 실제 IAM 사용자·Role 이름은 저장소에 없음 |

기본 리전은 `ap-northeast-2`(서울)이다.

### 4.2 계정 및 권한 준비

1. 팀 또는 조직 AWS 계정을 준비하고 Root 계정에 MFA를 적용한다.
2. 일상적인 작업에 Root Access Key를 사용하지 않는다.
3. 운영 EC2에는 가능하면 IAM Role을 연결해 임시 자격 증명을 사용한다.
4. 환경 변수 방식이 필요한 경우 프로젝트 전용 IAM 사용자를 만들고 최소 권한만 부여한다.
5. AWS Budget 및 비용 알림을 설정한다.

AWS는 Root 사용자의 장기 Access Key 대신 IAM Role과 임시 자격 증명 사용을 권장한다. 참고: [AWS 보안 자격 증명](https://docs.aws.amazon.com/IAM/latest/UserGuide/security-creds.html), [최소 권한 정책](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html)

보안 그룹은 다음 원칙으로 관리한다.

- `22/tcp`: 관리자 고정 IP 또는 VPN 대역만 허용한다.
- `80/tcp`, `443/tcp`: 서비스 공개 범위에 맞게 허용한다.
- LiveKit RTC 포트는 실제 통신 요구 범위만 공개한다.
- MySQL `3306`, Redis `6379`, RabbitMQ `5672`를 불필요하게 인터넷 전체에 공개하지 않는다.
- 가능하면 SSH 대신 Session Manager 또는 EC2 Instance Connect 사용을 검토한다.

### 4.4 S3

확인된 운영 버킷 사용 이력은 다음과 같다.

```text
Bucket: gordi-app-bucket
Region: ap-northeast-2
상품 이미지: GARMENT_S3_BUCKET
가상 착장 결과: TRYON_S3_BUCKET
가상 착장 기본 Prefix: fittings
```

`ai/.env` 설정 예시는 다음과 같다.

```env
AWS_REGION=ap-northeast-2
AWS_ACCESS_KEY_ID=<IAM access key 또는 미설정/EC2 IAM Role 사용>
AWS_SECRET_ACCESS_KEY=<IAM secret 또는 미설정/EC2 IAM Role 사용>
GARMENT_S3_BUCKET=gordi-app-bucket
TRYON_S3_BUCKET=gordi-app-bucket
TRYON_S3_KEY_PREFIX=fittings
```

애플리케이션 코드에서 확인되는 S3 작업은 `PutObject`와 `HeadObject`이다. IAM 권한은 최소한 다음 동작을 고려해 버킷과 Prefix 단위로 제한한다.

- `s3:PutObject`: 상품 및 가상 착장 이미지 업로드
- `s3:GetObject`: `HeadObject`를 포함한 객체 존재 및 Metadata 확인
- `s3:ListBucket`: 운영 점검에 필요한 경우에만 부여

`s3:*` 또는 모든 리소스 `*` 권한을 운영 애플리케이션에 부여하지 않는다.

상품 업로드 도구는 객체에 Content-Type, SHA-256 Metadata 및 SSE-S3 `AES256`을 적용하며 기존 객체를 무조건 덮어쓰지 않는다. S3 버킷은 Private과 Block Public Access를 유지한다. 참고: [S3 접근 관리](https://docs.aws.amazon.com/AmazonS3/latest/userguide/security-access-management.html), [S3 Block Public Access](https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html)

- Distribution ID: `[팀 확인 필요]`

## 5. LiveKit Server

### 5.1 사용 형태

프로젝트는 LiveKit Cloud가 아니라 `livekit/livekit-server:latest` Docker 이미지를 EC2에서 자체 호스팅한다. 따라서 LiveKit Cloud 가입이나 프로젝트 생성은 현재 구성상 필요하지 않다.

공식 참고 문서: [LiveKit Self-hosting](https://docs.livekit.io/transport/self-hosting/)

### 5.2 필요한 설정

```env
LIVEKIT_API_KEY=<임의의 서비스 Key>
LIVEKIT_API_SECRET=<충분히 긴 무작위 Secret, 프로젝트 기준 32바이트 이상>
LIVEKIT_SERVER_URL=wss://<서비스 도메인>/livekit
LIVEKIT_USE_EXTERNAL_IP=true
LIVEKIT_TOKEN_EXPIRATION=600000
LIVEKIT_ROOM_NAME_PREFIX=gordi-room-
```

Backend와 `docker-compose.prod.yml`의 LiveKit Server 설정은 반드시 동일한 API Key와 Secret을 사용해야 한다.

### 5.3 네트워크 설정

| 포트 | 프로토콜 | 용도 |
| --- | --- | --- |
| `7880` | TCP | LiveKit Signal/WebSocket, Nginx `/livekit/`로 Proxy |
| `7881` | TCP | RTC TCP |
| `50000-50100` | UDP | RTC Media |

운영 환경에서는 `LIVEKIT_USE_EXTERNAL_IP=true`를 사용하고 보안 그룹과 서버 방화벽에 RTC 포트를 반영한다. 서비스 페이지가 HTTPS이면 LiveKit도 `wss://`로 연결해야 한다.

### 5.4 보안 및 인수인계

- 로컬 기본값인 `devkey`와 예제 Secret을 운영에서 사용하지 않는다.
- API Secret은 Git에 저장하지 않고 Jenkins `backend-env-file`에서 관리한다.
- API Key 또는 Secret 변경 시 Backend와 LiveKit 컨테이너를 함께 재배포한다.
- 현재 Docker 이미지가 `latest`이므로 최종 운영 전에 검증된 버전으로 고정하는 것을 권장한다.
- LiveKit 서버 관리 담당자와 Key 회전 절차: `[팀 확인 필요]`

## 7. Jenkins

### 7.1 사용 형태

Jenkins는 EC2에 자체 호스팅하는 CI/CD 서버이므로 외부 SaaS 가입은 필요하지 않다. Jenkins 관리자에게 사용자 계정을 발급받고 Job 조회·실행 또는 관리 권한을 부여받아야 한다.

Pipeline은 저장소 루트의 `Jenkinsfile`을 사용한다.

### 7.2 필요한 Credential

Jenkins `Manage Jenkins > Credentials`에서 다음 **Secret file** Credential을 생성한다.

| Credential ID | 파일 내용 | Workspace 생성 위치 |
| --- | --- | --- |
| `backend-env-file` | Backend 및 공통 운영 환경 변수 | 루트 `.env` |
| `frontend-env-file` | Vite 빌드 환경 변수 | `frontend/.env` |
| `ai-env-file` | OpenRouter, AWS, 모델 및 AI 설정 | `ai/.env` |

공식 참고 문서: [Jenkins Credentials](https://www.jenkins.io/doc/book/using/using-credentials/)

### 7.3 Pipeline 준비사항

- Jenkins Agent에서 Git을 사용할 수 있어야 한다.
- Jenkins Agent 또는 Jenkins가 실행되는 호스트에서 Docker 및 Docker Compose를 사용할 수 있어야 한다.
- Jenkins 실행 사용자가 Docker Daemon을 사용할 권한이 있어야 한다.
- Gradle 테스트 컨테이너와 Docker Build가 사용할 충분한 디스크 공간이 필요하다.
- GitLab Webhook 요청이 Jenkins Endpoint에 도달할 수 있어야 한다.
- Pipeline Job은 저장소의 `Jenkinsfile`을 읽도록 구성한다.
- GitLab Clone에 인증이 필요한 경우 Jenkins SCM Credential을 별도로 등록한다.

### 7.4 Credential 보안

- Credential 값 자체를 Jenkins Console Log에 출력하지 않는다.
- Jenkins Credential은 가능한 가장 좁은 Folder 또는 Job Scope로 제한한다.
- `backend-env-file`, `frontend-env-file`, `ai-env-file`의 실제 파일은 Git에 추가하지 않는다.
- 환경 파일 변경 후에는 해당 컨테이너를 재생성해야 한다.
- Jenkins 관리자, Job 관리자, Credential 관리자 권한을 서로 구분한다.

## 8. Docker Hub

프로젝트는 다음 공개 이미지를 사용한다.

- `eclipse-temurin:21-jdk-alpine`
- `node:22-alpine`
- `nginx:alpine`
- `python:3.12-slim`
- `mysql:8.4`
- `redis:7-alpine`
- `rabbitmq:4-management-alpine`
- `livekit/livekit-server:latest`

현재 Pipeline은 자체 이미지를 Docker Hub에 Push하지 않고 EC2에서 직접 빌드한다. 따라서 공개 이미지 Pull만 수행할 경우 Docker Hub 계정은 필수가 아니다.

다만 Pull 제한 또는 Private Registry를 사용할 경우 Docker Hub 계정과 Personal Access Token을 준비한다. 자동화에는 계정 비밀번호 대신 최소 권한의 PAT를 사용한다.

공식 참고 문서: [Docker Hub Personal Access Token](https://docs.docker.com/security/access-tokens/)

```bash
docker login --username <Docker Hub 사용자명>
# Password 입력란에 PAT 입력
```

PAT를 사용할 경우 Jenkins의 Secret Text 또는 Username/Password Credential로 저장하며 저장소에 기록하지 않는다.

## 9. Discord GitLab 알림

Backend service: http://localhost:8100
