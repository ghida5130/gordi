# GitLab 소스 클론 이후 빌드 및 배포 환경 정리

이 문서는 GitLab에서 프로젝트 소스를 클론한 이후 Backend, Frontend, AI 서비스를 빌드하고 배포하는 데 필요한 실행 환경, 환경 변수, 배포 특이사항 및 주요 설정 파일을 정리한 문서이다.

> 보안 주의: 실제 비밀번호, API Key, Secret 값은 문서와 Git 저장소에 기록하지 않는다. 운영 값은 Jenkins Credential 및 서버의 `.env` 파일로 관리한다.

## 1. Backend

### 1.1 사용한 JVM, 웹서버, WAS 및 버전

| 구분 | 제품 및 버전 | 주요 설정 |

### 1.3 배포 시 특이사항

- Backend는 멀티 스테이지 Docker 빌드를 사용한다. 첫 단계에서 Gradle로 실행형 JAR을 만들고 두 번째 단계에서 `java -jar app.jar`로 실행한다.
- Docker 이미지 빌드에서는 `./gradlew clean bootJar -x test`를 사용해 테스트를 제외한다. 대신 Jenkins의 Backend 테스트 단계에서 `./gradlew test --no-daemon`을 먼저 수행한다.
- 운영 배포 시 `SPRING_PROFILES_ACTIVE=prod`가 Docker Compose에 의해 지정된다.
- Backend 컨테이너는 호스트 포트를 직접 공개하지 않는다. 외부 API 요청은 Nginx의 `/api/`, WebSocket 요청은 `/ws/`를 통해 전달된다.
- WebSocket Reverse Proxy는 HTTP/1.1 Upgrade 헤더를 사용하며 읽기 및 쓰기 제한시간을 3600초로 설정한다.
- MySQL, Redis, RabbitMQ와 애플리케이션 컨테이너는 외부 Docker 네트워크인 `app-network`에 참여한다. 최초 실행 전 네트워크를 생성해야 한다.

```bash
docker network create app-network
```

- Jenkins는 `backend/` 변경 시 Backend를 다시 빌드한다. `docker-compose.prod.yml` 또는 `Jenkinsfile`이 변경되면 Backend, Frontend, AI 전체를 재빌드한다.
- 운영 `.env`는 Git에 커밋하지 않고 Jenkins의 `backend-env-file` Credential을 통해 주입한다.
- `INTERNAL_API_KEY`는 Backend와 AI 서버에 반드시 동일한 값으로 설정한다.
- 운영에서도 현재 `spring.jpa.hibernate.ddl-auto=update`와 `spring.jpa.show-sql=true`가 적용된다. 안정적인 운영을 위해 최종 배포 전 각각 `validate` 또는 `none`, `false` 적용 여부를 검토한다.
- `server.forward-headers-strategy=framework`를 사용하므로 Nginx가 전달하는 `X-Forwarded-*` 헤더를 기준으로 외부 요청 정보를 처리한다.

## 2. Frontend

### 2.1 사용한 런타임, 웹서버 및 버전

| 구분 | 제품 및 버전 | 주요 설정 |
| --- | --- | --- |
| 빌드 런타임 | Node.js 22 | Docker 이미지 `node:22-alpine` |
| UI 프레임워크 | React | 선언 버전 `^19.2.7`, Lock 설치 버전 `19.2.8` |
| 라우팅 | React Router DOM `^7.18.1` | SPA 라우팅 |
| 빌드 도구 | Vite | 선언 버전 `^8.1.1`, Lock 설치 버전 `8.1.5` |
| CSS 프레임워크 | Tailwind CSS `^4.3.3` | Vite Plugin 사용 |
| 웹서버 | Nginx Alpine | Docker 이미지 `nginx:alpine` |
| 서비스 포트 | `80` | Nginx 정적 파일 서비스 |
| 정적 파일 경로 | `/usr/share/nginx/html` | Vite의 `dist` 결과 복사 |
| 기본 문서 | `index.html` | SPA Fallback 적용 |
| IDE | Visual Studio Code `[실제 사용 버전 확인 필요]` | 저장소에서 IDE 버전 확인 불가 |

`nginx:alpine`은 패치 버전이 고정되지 않은 태그이므로 정확한 Nginx 버전은 최종 빌드 서버 또는 실행 중인 컨테이너에서 `nginx -v`로 확인해야 한다.

### 2.2 빌드 시 사용되는 환경 변수

Frontend에서 실제 사용하는 사용자 정의 환경 변수는 다음과 같다.

| 환경 변수 | 기본값 | 설명 |
| --- | --- | --- |
| `VITE_API_BASE_URL` | `/api` | Backend API 기본 주소 |

운영 환경 예시는 다음과 같다.

```env
VITE_API_BASE_URL=/api
```

개발 서버에서 Backend에 직접 연결하는 경우 다음과 같이 지정할 수 있다.

```env
VITE_API_BASE_URL=http://localhost:8080/api
```

Vite 환경 변수는 반드시 `VITE_`로 시작해야 하며, 브라우저용 정적 파일을 빌드할 때 값이 포함된다. 따라서 DB 비밀번호, API Secret과 같은 보안 값은 Frontend 환경 변수에 저장하면 안 된다.

루트 `.env.example`에는 `VITE_AI_API_BASE_URL`도 정의되어 있지만 현재 Frontend 소스에서는 직접 참조하지 않는다. AI 기능은 Backend API 또는 Nginx의 `/ai/` 경로를 이용한다.

### 2.3 배포 시 특이사항

- Frontend는 `node:22-alpine`에서 `npm ci`와 `npm run build`를 실행한 후 생성된 `dist` 디렉터리만 Nginx 이미지로 복사한다.
- 운영 컨테이너에서는 Node.js 개발 서버가 실행되지 않으며 Nginx가 정적 파일만 서비스한다.
- Frontend 컨테이너 내부 포트는 80이며 사용자는 루트 Nginx Reverse Proxy를 통해 접속한다.
- React Router 경로에서 브라우저 새로고침 시 404가 발생하지 않도록 존재하지 않는 경로를 `index.html`로 전달한다.

```nginx
try_files $uri $uri/ /index.html;
```

- `/health` 요청은 외부 의존성 없이 `200 ok`를 반환한다.
- `VITE_*` 값은 빌드 시점에 정적 JavaScript 파일에 포함된다. 실행 중인 Nginx 컨테이너의 `env_file`만 변경해서는 반영되지 않으므로 환경 변수 변경 후 Frontend 이미지를 다시 빌드해야 한다.
- 기본 API 주소가 `/api`이므로 동일 도메인의 Nginx Reverse Proxy를 통해 Backend에 접근한다.
- Jenkins는 `frontend/` 변경 시 Frontend 이미지를 다시 빌드하고 배포한다.
- Jenkins의 `frontend-env-file` Credential은 `frontend/.env`로 복사된다. 해당 값이 필요한 경우 `npm run build` 이전에 Docker 빌드 컨텍스트에 포함되어야 한다.
- Frontend 컨테이너와 루트 Reverse Proxy는 모두 `nginx:alpine`을 사용한다. 이미지 패치 버전이 고정되어 있지 않아 빌드 시점에 따라 결과가 달라질 수 있다.

### 2.4 DB 접속 정보 및 주요 프로퍼티 파일

Frontend는 MySQL, Redis 또는 다른 데이터 저장소에 직접 접속하지 않는다. 모든 데이터 요청은 Backend API를 통해 처리하므로 Frontend에 DB 계정이나 DB 비밀번호를 설정하지 않는다.

| 파일 | 용도 |
| --- | --- |
| `frontend/.env.example` | Backend API 기본 주소 정의 |
| `frontend/src/lib/httpClient.js` | Axios 기본 URL, 요청 제한시간 및 인증 토큰 처리 정의 |
| `frontend/src/api/request.js` | 공개 및 인증 API 클라이언트 구성 |
| `frontend/package.json` | React, Vite, Tailwind CSS 및 기타 패키지 버전 정의 |
| `frontend/package-lock.json` | 실제 설치되는 npm 패키지 버전 고정 |
| `frontend/vite.config.js` | React, Tailwind CSS Plugin 및 `@` 경로 Alias 설정 |
| `frontend/Dockerfile` | Node.js 빌드 환경과 Nginx 정적 배포 환경 정의 |
| `frontend/default.conf` | 정적 파일 경로, SPA Fallback 및 헬스 체크 정의 |
| `default.conf` | `/`, `/api/`, `/ai/`, `/ws/`, `/livekit/` Reverse Proxy 대상 정의 |

Frontend에서 사용하는 Access Token은 브라우저 저장소를 통해 관리하며 Refresh Token은 Backend가 발급하는 쿠키를 사용한다. 해당 값도 DB 접속 계정과 무관하며 Frontend 환경 파일에 하드코딩하지 않는다.

### 3.3 배포 시 특이사항

- AI 환경 변수는 `ai/.env`로 분리하며 Jenkins의 `ai-env-file` Credential을 통해 배포 시 생성한다.
- Backend와 공유하는 `INTERNAL_API_KEY`는 루트 `.env`, `ai/.env` 또는 Compose 환경에 동일하게 설정해야 한다.
- AI 컨테이너는 호스트 포트를 직접 공개하지 않는다. 외부 요청은 Nginx의 `/ai/` 경로로 전달된다.
- Backend 내부 요청은 외부 도메인이 아니라 Docker 서비스명 `http://gordi-ai:8000`을 사용한다.
- AI API Prefix는 운영 Compose에서 `/ai/v1`로 설정한다. 애플리케이션의 로컬 기본 Prefix인 `/api/v1`과 다르므로 헬스 체크 및 API URL 작성 시 주의해야 한다.
- 임베딩 인덱스 `catalog-embeddings.json`은 Git만으로 서버에 배포되지 않는다. EC2 호스트에 별도로 배치한 후 AI 컨테이너의 `/app/catalog_index`에 읽기 전용으로 마운트한다.
- 임베딩 모델과 차원은 인덱스 생성 당시 값과 일치해야 한다. 현재 기본 규격은 `google/gemini-embedding-2`, 768차원이다.
- 가상 착장 결과 디렉터리 `/app/tryon_results`는 호스트 볼륨으로 마운트한다.
- `RECOMMENDATION_IMAGE_ALLOWED_HOSTS`에는 실제 상품 이미지 및 결과 이미지 도메인을 등록해야 한다. 등록되지 않은 호스트의 이미지는 AI가 가져오지 못한다.
- 운영에서는 인증 없는 데모 화면 노출을 막기 위해 `ENABLE_RECOMMENDATION_DEMO=false`를 유지한다.
- VLM 재정렬을 활성화하면 AI 응답 시간이 증가할 수 있으므로 Backend의 `AI_READ_TIMEOUT_MS`도 함께 조정해야 한다.
- `.env`만 변경해도 실행 중인 컨테이너에는 자동으로 반영되지 않는다. Jenkins 배포를 다시 실행하거나 AI 컨테이너를 재생성해야 한다.
- 필수 API Key, 임베딩 인덱스 또는 모델 설정이 잘못되면 추천 API가 `503 Service Unavailable`을 반환할 수 있다.
- Docker Compose 변경 또는 Jenkinsfile 변경 시 변경 감지 정책에 의해 Backend, Frontend, AI 전체가 재빌드된다.
